# 代码审阅与 HPC / AI4S 升级建议（2026-11-22）

> 范围：仓库当前 `engineering-mvp` 分支（约 25.5k 行 Python/C++/CUDA）。
> 目标：在**不改变现有数值契约**的前提下，判断代码离 HPC / AI4S 还差什么，
> 并记录本轮已经落地的环境与构建修复。
>
> 相关环境文档：[WSL开发环境.md](WSL开发环境.md)。

## 0. 结论摘要

| 维度 | 评价 | 说明 |
|---|---|---|
| 分层与契约 | 好 | `desktop → worker → products`，硬件接口与 mock 隔离清楚；worker 不依赖 Qt |
| 数值单一来源 | 较好 | `products/optics` 是唯一 Zernike/前向实现；torch/numpy 前向有金标测试 |
| 可复现性 | 中 | 有三套 Python 基线，但 PySide6 与 glibc 的平台差异未写清（本轮已修） |
| HPC 就绪度 | 低-中 | 有 CUDA 求解器与 OpenMPI，但 GPU 求解器没绑定到 Python，且每次目标函数都有 D2H 同步 |
| AI4S 就绪度 | 中 | torch 前向与 CNN 已存在，但只有 3 项、无 GPU 训练/导出/不确定度闭环 |
| 工程卫生 | 中 | 测试基线扎实；文档索引有失效链接，依赖文件重复，WSL/conda 污染会进构建 |

一句话：**先把“GPU 求解器 → Python”打通，再谈多节点和 AI 代理模型**；
否则 HPC/AI4S 会在两套无法互相验证的实现之间重复投入。

## 1. 值得保留的设计

1. `products/optics/forward.py` + `products/optics/zernike.py` 收口后，
   `ml.traditional` 只做兼容 re-export，方向正确。
2. `ml/tests/test_forward_equivalence.py` 用 float64 对 torch 与 numpy 前向做
   逐元素对照，是 AI4S 最关键的“同一物理、同一金标”基础设施。
3. `products/pd/core.py` 把目标函数/边界/BOBYQA 只写一次，`batch.py` 复用，
   避免 Web 时代的多份实现。
4. `framework/` 的 `ForwardModel / InverseSolver / SensitivityBuilder /
   ControlSolver` 契约，是把 Python 原型迁到 C++/HPC 的正确接缝。
5. `desktop/worker.py` 不 import PySide6，任务通过 JSON envelope 通信，
   为“GUI 在 Windows、计算在 Linux 集群”留下可能。
6. 数据标签（`CORE-VERIFIED` / `EXTERNAL-CHECK` / `FEA-PROVISIONAL` /
   `UNVERIFIED`）写进了结果与文档，避免把合成当实测。

## 2. 问题清单

### P0（会直接阻断当前目标）

| ID | 位置 | 问题 | 本轮动作 / 建议 |
|---|---|---|---|
| P0-1 | `pyproject.toml`、`requirements-runtime.txt`、`constraints.txt` | 固定 `PySide6==6.12.0`，但其 Linux wheel 要求 glibc ≥ 2.34；Ubuntu 20.04 是 2.31，直接装不上；同时 6.12 要求 Python ≥ 3.10，与“3.8 基线”矛盾 | 已按 `sys_platform` 分开：Windows 6.12.0 / Linux 6.9.3；注释写清平台边界 |
| P0-2 | `CMakeLists.txt`、`numerics/CMakeLists.txt` | WSL 的 PATH 含 Windows conda，CMake 会把 `/mnt/c/.../GTestConfig.cmake`（MSVC ABI）当成 Linux GTest；本轮首次 configure 已复现 | 已改为只在 `/usr/lib` 找系统 GTest；`CMakePresets.json` 忽略 `/mnt/c`…`/mnt/g`；并修了 Eigen 3.3 不支持的 `Vector{{...}}` 写法 |
| P0-3 | `framework/plugins/phase_diversity/phase_adapter.cpp`、`src/phase_diversity.cu` | CUDA 求解器只暴露给 C++ framework，Python/AI4S 无法调用；`numerics/bindings` 只绑定线性代数 | 建议新增 pybind11 模块 `telescope_pd`（`evaluate` / `solve` / `preprocess`），用同一组金标与 Python 前向对照 |
| P0-4 | `src/phase_diversity.cu`（`PhaseDiversitySolver::evaluate`） | 每次目标函数：`generate_frames` → kernel → `cudaMemcpy` 回 host → host 求和；NLopt 在 host 串行调用，GPU 大部分时间在等同步 | 建议：批量多起点一次发射、`cudaMemcpyAsync` + pinned memory、多流；或直接把 NLopt 换到设备端/批量评估 |

## 4. HPC 路线

### 阶段 1：单节点 GPU（现在就能做）

1. **打通 Python ↔ CUDA**：新增 pybind11 模块，复用 `PhaseDiversitySolver`；
   暴露 `preprocess_frames`、`evaluate(coeff)`、`solve(data, defocus)`。
2. **批量多起点**：一次把 N 个初值传入 GPU，kernel 内评估 N 个代价；
   避免 P0-4 的逐次 D2H。
3. **异步/多流**：`cudaMemcpyAsync` + pinned host buffer；帧生成与代价归约分流域。
4. **性能门禁**：固定 256²/5 帧/3 起点的基准，记录 `scripts/benchmark_pd.py`
   的 CPU 基线，GPU 目标 ≥10×；用 `ncu` 看 SM 占用与访存。
5. **数据格式**：PSF 栈/FEA 面形新写 HDF5；FITS 仍作交换格式。

### 阶段 2：多节点（有集群后）

1. 以“高度角 / 机构 DOF / 多起点”为 MPI 任务粒度，rank 之间只交换
   S 矩阵与代价，不交换整帧；
2. 用 `h5py` 的并行 HDF5 或每 rank 独立文件 + 汇总；
3. Slurm `${SLURM_ARRAY_TASK_ID}` 映射到 elevation/DOF，结果带 `RunManifest`；
4. 固定 seed、记录 CUDA/驱动/编译器版本，保证可复现。

### 阶段 3：与 AI4S 合流

- GPU 求解器提供“真值/精修”，torch 代理模型提供“初值/不确定度”；
- 同一份 6 项 Zernike 项表和同一组金标贯穿 C++/CUDA/torch；
- 不在集群上再引入第二套数组/并行框架（JAX/CuPy/Spark）。

## 5. AI4S 路线

| 优先级 | 事项 | 验收 |
|---|---|---|
| 1 | 6 项可微前向 + 6 维 CNN | 与 `products.optics.forward` 6 项金标 `max|Δ| < 1e-6` |
| 1 | CNN 初值 + PD 精修（已有 `ml/two_stage.py`）接入批量反演 | 相同精度下，BOBYQA 评估数下降 ≥50% |
| 2 | 不确定度（MC dropout / ensemble） | 对低 SNR/遮挡帧给出可校准的置信区间 |
| 2 | ONNX 导出 + 固定 opset | `onnxruntime` CPU 推理与 torch 输出一致 |
| 3 | 数据/实验登记（RunManifest 已有） | 每次训练可追溯数据版本、seed、超参、金标 |
| 3 | 代理模型替代部分前向评估 | 在留出集上误差可控，且不替代最终 PD 精修 |

4 GB 显存的现实约束：CNN 训练用小网格/AMP/梯度累积；256² 批量反演优先放
CUDA 求解器，不把大 batch 塞进 torch 训练。
